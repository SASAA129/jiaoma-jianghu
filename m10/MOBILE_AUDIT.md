# 《椒麻江湖》M10 手机适配体检报告

- 体检对象：本地 M10（`/workspace/game-m10`，http://localhost:8089），代码与线上 /m10/ 一致
- 体检时间：2026-10-17（北京时间）
- 工具：Playwright + Chromium 手机模拟（hasTouch / isMobile / deviceScaleFactor 3）
  - iPhone 13 竖屏 390×844、横屏 844×390；安卓 360×800（竖屏）
- 流程（全部用触摸 tap）：标题 → 新游戏 → 火锅店点地走动 → 直接点 NPC 立绘对话 → 战斗（攻击点敌人、武学菜单、道具对同伴）→ 「地图」按钮 → 传送到老码头夜市 → 刷新 → 「继续游戏」读档 → `?chapter=3` 三个小游戏
- **流程本身全部走通，三台设备全程 0 个 JS 报错。** 问题集中在“看不清、点不准、加载慢”，另外顺带发现一个剧情数据 bug（第 2 条）。
- 截图：`screenshots/mobile_audit/`（文件名前缀为设备；A_～E_ 开头的是标注图）；原始数据：`screenshots/mobile_audit/audit_raw.json`
- 本次没有改动 game-m10 的任何代码或素材，只新增了本文件和 `screenshots/mobile_audit/`。

工作量按程序员 Bot 人日估：XS ≤ 1 小时，S ≤ 0.5 天，M 1–2 天，L 3 天以上。

## P0：必须先解决（影响能不能玩）

### 1. 整个界面跟着 1536×1024 画布等比缩小：字小到读不了，按钮小到点不中
- **现象**：`game.js resize()` 把整个 `#stage`（画布 + 全部 DOM 界面）按 `min(vw/1536, vh/1024)` 缩放。手机上的缩放比例：iPhone 横屏 **0.381**，iPhone 竖屏 **0.254**，安卓竖屏 **0.234**。界面写的是 1536 宽设计稿里的 px，到手机上被一起缩小。
- **字号（换算成 CSS px，标准 ≥14）**：

  | 设备 | 页面文字最小 / 中位 | 对话正文（CSS 30px） | 每屏小于 14px 的文字 |
  |---|---|---|---|
  | iPhone 横屏 | 4.6 / 6.9 px | 11.4 px | 30/30（全部） |
  | iPhone 竖屏 | 3.0 / 4.6 px | 7.6 px | 31/31 |
  | 安卓 360 | 2.8 / 4.2 px | 7.0 px | 31/31 |

  最小的是操作提示、出手顺序条上的「身法 16」、地图图例（4.6px）。

- **可点区域（标准 ≥44×44）**：每个界面里的每一个按钮都不达标。

  | 按钮 | iPhone 横屏 | iPhone 竖屏 | 安卓 360 |
  |---|---|---|---|
  | 底部 背包/人物/江湖志/地图/菜单 | 29.7×29.7 | — | 18.3×18.3 |
  | 战斗 攻击/武学/防御/道具/撤退 | 41.9×41.9 | 27.9×27.9 | 25.8×25.8 |
  | 战斗 道具「返回」 | 34.3×33.5 | 22.9×22.3 | 21.1×20.6 |
  | 大地图节点 | 32×32 | 21.3×21.3 | 19.7×19.7 |
  | 地图「关闭（M）」 | 62.5×21.7 | 41.6×14.5 | 38.4×13.4 |
  | 右侧探索列表每一项 | 92.9×13.7 | 62×9.1 | 57.2×8.4 |
  | 「重置存档」 | 92.9×10.3 | 62×6.9 | 57.2×6.3 |
  | 小游戏「先不玩了」 | 40.4×15.2 | 26.9×10.2 | 24.8×9.4 |

- **截图**：`B_targets_iphone13_landscape_03_shop.png`、`B_targets_iphone13_landscape_06_battle.png`、`B_targets_iphone13_landscape_09_map.png`（红框是不达标的区域，旁边标了尺寸）、`iphone13_landscape_05_dialog.png`
- **建议改法**：
  1. 界面和世界分成两层：画布（世界）继续等比缩放；HUD、对话框、面板、战斗指令、地图按钮挪到不缩放的 `#hud` 层，用 CSS px、vh 或 `clamp()` 布局，正文 ≥16px、辅助字 ≥14px、按钮 ≥44px（主按钮 52–64px）。
  2. 横屏以 844×390 为基准重新排版，这正好对应 M11 方案里的“横屏单手布局”。大地图节点的可点区域扩到 ≥44px（图标可以不变，加透明热区）。
  3. 一个过渡做法：`viewScale < 0.6` 时给 UI 层乘一个补偿系数 `1/viewScale × 0.4~0.5`。改得快，但会挡住画面，只适合临时用。
- **工作量**：L（4–6 人日，包含对话框、战斗、地图、面板、小游戏五类界面的重排和回归测试；和 M11 菜单框架一起做）

### 2. 【顺带发现，不是手机问题】第三、四章的支线事件放的是第五章的剧情和小游戏
- **现象**：`data/dialogue.js` 把 CH3–CH6 的对白按节点 id 直接合并（`D.nodes[k] = Cx.nodes[k]`）。CH3、CH4、CH5 都用了 `E1_1…E3_after` 这类同名 id，一共 **19 个 id 冲突**，后加载的第五章把前面的覆盖了。实测 `?chapter=3`：
  - 点「桅杆·认星位」弹出的是第五章的“**假账·东厢账房**”（ledger），不是认星（stars）；
  - 点「船舷·下网」弹出的是第五章的“**后厨**”颠勺（kitchen），不是下网（net）；
  - 第四章同理（E1/E2/E3 都会被替换成第五章的版本）。
  - M9 的数据完全一样（已锁定的线上 /m9/ 也有这个问题）。selftest 里没有检查这一项，所以一直没发现。
- **截图**：`iphone13_landscape_mg_ledger.png`、`iphone13_landscape_mg_kitchen.png`、`E_overview_landscape.png`（下面两格）
- **建议改法**：合并时给节点加章节前缀（`c3.E1_1`），或者让 entries 和 do 里引用的节点按章节作用域查找。同时在 selftest 里加两项：“合并后节点 id 不冲突”和“第三章三个事件弹出对应的小游戏”。
- **工作量**：S（半天，含测试）。这一条要改 M10 或 M11 的数据，需要用户确认。

### 3. 加载 34 MB，开局一次性下载 6 章全部美术；4G 下要 28 秒，期间显示几何占位图，没有进度提示
- **实测（CDP 限速，关闭缓存）**：

  | 网络 | 标题卡出现 | 全部图片就绪 | 请求数 | 体积 |
  |---|---|---|---|---|
  | 4G 常规 10 Mbps / 40 ms | 0.6 s | **27.7 s** | 90 | **34.2 MB**（图片 33.8 MB） |
  | 慢 4G 1.6 Mbps / 150 ms | — | 估算约 **171 s** | | |

  最大的几张：bg_worldmap 3.2 MB，bg_arena 2.9，bg_village 2.9，bg_market 2.8，cg_ending 2.6，bg_river 2.6，bg_hq 2.5，都是 1536×1024 的 PNG。
- **体验问题**：标题卡 0.6 秒就能点。玩家在 5 秒时点「新游戏」，还有 27 张图没到，场景里显示线框格子和“（占位）bg_room.png 未到位”。整个过程没有加载进度。
- **截图**：`iphone13_landscape_18_4g_title_2s.png`、`iphone13_landscape_19_4g_newgame_4s.png`
- **建议改法**：
  1. PNG 转 WebP（q≈80，背景图预计能压掉 70–85%，总量降到 6–9 MB），PNG 留作回退；
  2. 按章节和场景懒加载：开局只加载标题、当前场景和三人立绘（约 4–5 MB），其他场景在进入前预取；
  3. 标题卡加加载进度条，当前场景没加载完时「新游戏」「继续」先置灰；
  4. 手机（视口 <1000 px）加载 0.5 倍分辨率的背景版本。
- **工作量**：M（1.5–2 人日，prep_assets 输出 WebP 和半分辨率版本，资源表改成分章加载）

### 4. 竖屏只用了屏幕的 30%，旋转提示很弱，而且可以点掉后继续玩
- **现象**：竖屏下画面缩成 0.254 / 0.234 倍，居中显示，上下两大片黑边（画面只占屏幕 30.8% / 30.0%）。`#rotate-hint` 是一条细横幅（“横屏体验更佳 · 点此关闭”），字号约 3–4 px，点掉以后游戏照样能玩，但所有字都在 3–5 px。
- **截图**：`C_portrait_letterbox.png`、`iphone13_portrait_01b_rotate_hint.png`、`android_360x800_01b_rotate_hint.png`、`iphone13_portrait_06_battle.png`
- **建议改法**：竖屏时显示全屏旋转引导（大图标 + 16px 以上文字），不提供关闭按钮。安卓 Chrome 在全屏后调用 `screen.orientation.lock('landscape')`，并在 PWA manifest 里写 `"orientation":"landscape"`。iOS 不能锁定方向，只能用引导页。以后如果要做竖屏版，是另一个独立项目。
- **工作量**：S（半天）

## P1：严重影响手感

### 5. 战斗选目标时只能按 Esc 返回，手机上一旦点了「攻击」就退不回去
- **现象**：`battle.js pick()` 的提示是“选择攻击目标（点敌人）　(Esc 返回)”，只有 `keydown Escape` 能取消。点战斗画布的空白处也没反应，触屏玩家点错「攻击」或「武学」就只能出这一招。
- **截图**：`iphone13_landscape_07_battle_skill.png`（流程里实测：提示文案就是 Esc）
- **建议改法**：选目标时在指令区放一个「返回」大按钮（≥44px），点空白处也算取消，提示文案改成“点敌人 · 点空白返回”。
- **工作量**：XS（1 小时）

### 6. 对话框挡住主角三人（遮住 49%–77%）
- **现象**：`#dialog` 固定在 `bottom:150px; left/right:150px`。对话时主角三人通常站在画面下半部分，实测在火锅店对话框盖住 小满 49%、飞飞 68%、胖弟 77%，三台设备一样（整体等比缩放）。说话的人常常被自己的对话框挡住。
- **截图**：`iphone13_landscape_05_dialog.png`、`iphone13_portrait_05_dialog.png`、`android_360x800_05_dialog.png`
- **建议改法**：对话框贴到屏幕底部（加 safe-area 内边距），高度不超过屏幕 28%。打开对话时，如果说话的人或主角落在对话框区域里，相机上移或场景整体平移 15%。按 M11 方案配半身立绘，用来替代被挡住的人物。
- **工作量**：S–M（0.5–1 人日）

### 7. 帧率：4 倍 CPU 降速下，走路 26 fps，战斗只有 11–12 fps（瓶颈在战斗渲染，不在骨骼）
- **实测（rAF 采样，iPhone 横屏视口，DPR 3）**：

  | 场景 | 1× | 4× | 6× |
  |---|---|---|---|
  | 火锅店走动·三人骨骼（默认） | 60 fps | **26.1 fps**（p95 50 ms） | 15.9 fps（p95 83 ms） |
  | 火锅店走动·骨骼全关 `?rig=0` | 60 | 28.6 | 16.8 |
  | 战斗·三人骨骼 | 57.6 | **11.6 fps**（p95 100 ms） | — |
  | 战斗·骨骼全关 | 52.1 | 12.1 | — |

  骨骼动画大约只占 10% 的开销。战斗在 1× 时已经掉帧，4× 下大约 12 fps，主要是每帧整张重画大背景、人物、圆盘和特效，画布按 DPR 3 的分辨率重绘（1755×1170 像素）。
- **建议改法**：画布 DPR 封顶 2（手机看不出区别，像素量减少约 55%）；背景和静态道具先画到离屏 canvas 缓存，每帧只画人物层；战斗画面静止时降到 30 fps 或者只在有动画时重绘；用 Performance 面板找出战斗里最耗时的绘制。
- **工作量**：M（1–2 人日）

### 8. 点地走路和点人物的命中率：坐标换算准确，但格子太小
- **实测**：触摸坐标换算正确，在 15 个随机格子中心点击，14 个正好命中，剩下 1 个是被交互物截住了（这是正常行为）。直接点 NPC 立绘可以打开对话，点敌人可以出招，点同伴可以用道具，都正常。
- 问题在格子大小：相邻格子中心只相距 26.4 px（iPhone 横屏）、17.6 px（iPhone 竖屏）、16.2 px（安卓）。按手指误差 σ≈2 mm（约 7.6 CSS px）模拟，点中想去那一格的概率分别是 **74% / 46% / 43%**。走路差一格问题不大，但点交互物、站位小游戏、选目标都会受影响。
- **建议改法**：交互物和 NPC 的热区不小于 44 CSS px；点击位置周围 24 px 内有交互物就吸附过去；选目标时目标身上显示大一些的高亮圈并可以点；点地涟漪已经有了，保留。
- **工作量**：S（半天）

## P2：体验瑕疵，建议在 M11 一起做

### 9. 没有处理刘海屏安全区
- **现象**：CSS 和 HTML 里都没有 `env(safe-area-inset-*)`（`viewport-fit=cover` 已经写了）。现在因为横屏两侧有 129 px 黑边，刘海（47 px）没压到内容，但底部的队伍卡和菜单按钮落在 Home 条区域（底部 21 px）里，上滑容易误触发系统手势。等第 1 条改成全屏 HUD 以后，左右两侧的按钮一定会被刘海挡住。
- **截图**：`A_safe_area_iphone13_landscape.png`（红色区域是安全区以外）、`A_safe_area_iphone13_portrait.png`
- **建议改法**：HUD 四边的 padding 用 `max(12px, env(safe-area-inset-left))` 这种写法；底部按钮额外留出 `env(safe-area-inset-bottom)`。
- **工作量**：S（半天，和第 1 条一起做）

### 10. 界面上留着键盘提示，还有一处功能只能用键盘
- **现象**：地图按钮写着「关闭（M）」；标题卡和探索面板写着“1/2/3 切换队长 · 空格交互 · G 网格 · E 编辑”；战斗里写着“Esc 返回”。核心功能里只有“战斗取消选目标”必须用键盘（见第 5 条），其他都有可以点的按钮：开地图有「地图」按钮，切队长可以点队伍卡，交互可以点物体或列表。
- **截图**：`iphone13_landscape_09_map.png`、`iphone13_landscape_01_title.png`
- **建议改法**：用 `@media (hover:none) and (pointer:coarse)` 或 `'ontouchstart' in window` 判断触屏，换成触屏文案（「关闭」、“点地面行走 · 点人物交谈”），隐藏 G/E 调试提示。
- **工作量**：XS

### 11. 有些信息只能悬停才看得到，触屏上的悬停样式会“粘住”
- **现象**：队伍卡的数值（“气血 920/1000　内力 610/800”）只放在 `title` 属性的悬停提示里，触屏上完全看不到。另外 CSS 有 8 条 `:hover` 规则（探索列表、动作菜单、对话选项、战斗指令、地图节点的徽标等），只影响样式，但在 iOS 上点过一次以后高亮会一直留着。
- **建议改法**：数值直接写在 HUD 或「伙伴」面板里；`:hover` 规则包进 `@media (hover:hover)`，触屏用 `:active` 做按下反馈。
- **工作量**：XS–S

### 12. 小游戏的按钮偏小，限时操作的按钮也太小
- **现象（iPhone 横屏 / 安卓）**：答题选项 385×22.5 / 237×13.8（够宽但不够高）；「先不玩了」40×15 / 25×9，而且贴着标题，容易误点退出；颠勺这类看时机的小游戏，「颠！」只有 76×32 / 47×20，看时机的玩法用这么小的按钮，手感很差。对山歌的流程走通了；认星和下网弹出的是错误的小游戏（第 2 条）。
- **截图**：`iphone13_landscape_mg_song.png`、`android_360x800_mg_kitchen.png`、`iphone13_portrait_mg_ledger.png`
- **建议改法**：选项高度 ≥48px；看时机的玩法改成点屏幕任意位置都算（或者按钮 ≥88px，放在拇指区）；「先不玩了」移到左上角，点了弹二次确认。
- **工作量**：S

## P3：小问题

### 13. 标题写着“还没有存档”，点「新游戏」却提示“会覆盖当前存档，再点一次确认”
- 原因：开机进场景时已经自动写了一次存档，但标题卡的文字是在那之前生成的。新玩家第一下点击会被吞掉。
- **截图**：`iphone13_landscape_19_4g_newgame_4s.png`
- **改法**：判断是否有存档时，以玩家真正推进过（例如有剧情 flag）为准，或者开机进场景时不写存档。**XS**

### 14. 「重置存档」挨着「三人骨骼动画」开关，按钮只有 6–10 px 高
- 已经有“点两次才确认”的保护，误触风险不大。手机版建议移进「设置」面板，加上明确的二次确认弹窗。**XS**（M11 的「设置」按钮会顺带解决）

### 15. 没有手动存档或读档的入口
- 目前只有自动存档，加上标题页的「继续游戏」。实测在夜市自动存档 → 刷新 → 继续 → 回到夜市，功能正常。M11 方案计划做 3 个手动存档位，现在不算 bug。**M**（等方案批准）

## 测试的局限
- 用的是 Chromium 模拟手机，不是真机上的 iOS Safari。iOS 有时会忽略 `user-scalable=no`，地址栏和工具栏伸缩也会改变可视高度，这两点要在真机上复测。
- 刘海和 Home 条是按 iPhone 13 的规格（横屏两侧 47 px、底部 21 px）画上去的示意，模拟器不会真的渲染出来。
- 4G 用的是 CDP 限速访问本机服务器，没有计入 CDN 和 TLS 的耗时，真机只会更慢。CPU 降速是相对这台测试机的倍率。

## 和 M11 方案（`game-design/jiaoma/mobile_m11_plan.md`）的关系
第 1、6、9、10、11、14 条和 M11 的“横屏单手布局”是同一件事，建议一起做。第 2、3、5 条和 M11 无关，可以先单独修（第 2、5 条各不超过半天）。
